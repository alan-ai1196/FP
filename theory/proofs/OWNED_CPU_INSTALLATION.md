## 1. Proposal truth and current installation authority have different times

At ordinary cursor t0, the executed finite native search proves an empirical
reference maximum over its registered constructor endpoints plus the actual
deployed baseline. Fresh persistence then advances the selected candidate
and comparator through new observations and registered learner updates.
At t>t0 the original proof is stale as a **current** class-maximum token.
Nothing proves that the trained successor still maximizes that old class,
or a new class of trained states. In particular, requiring both an unchanged
current constructor-endpoint proof and nonempty fresh learning would confuse
two different propositions and can make their intended composition impossible.

The usable historical proposition is: this owned lineage was the selected
member of that completely evaluated class at t0. Runtime retains its issued
proof, exact comparison rows, actual constructor/profile state and lineage.
It does not accept a caller-written certificate or merely equal graph.
The two persistence identities must start at t0 with exactly the selected
reference candidate and baseline states. Their finite counterparts have
executed their own registered construction and event-level relations.
Both identities continue on the same four learners and exogenous schedule.

Consequently the install can establish the conjunction:

1. exact class selection **at the proposal boundary**;
2. two current same-path historical persistence crossings on the continuously
   executed learner paths, under their explicit stochastic assumptions;
3. current numerical/range relations and reachable physical installation.

This conjunction is not a current global optimum or `CERTIFIED_COMPLETE`.
`verify_reference_class_proof` continues to reject the stale token in that
current-optimum role. `install_cpu` retrieves its own historical issuance
only as the first premise and independently checks the remaining premises.
A same-graph newborn cannot inherit another lineage's proposal or wealth.

## 2. The registered physical transition

[`CpuInstallContract`](../../src/reference_compiler/fp_reference/installation.py)
is part of the immutable `OnlineContract` and therefore the Runtime claim
identity before any execution. It fixes:

- existing raw learner buffers, with no state reset/recast/quantization;
- retention of all shadows and demotion of the previous deployed lineage;
- closure of all reference searches, retaining their frontier/history;
- invalidation of all live persistence identities, without rebasing wealth
  or refunding any alpha;
- one serialized CPython root publication and atomic buffer-lease transfer;
- explicit installation work and workspace resource roles.

The roles are experiment parameters fixed beforehand. They do not grant a
target-resource phase interpretation for work charged to another role.
The current work debit is a fixed function of retained packed payload size
and record/object counts in this partial reference machine. It is paid before
the fallible install computation. It does not bound total executed CPython
instructions, elapsed time or bit-time; complete host accounting stays open.

The physical primitive transfers leases on existing buffers; it does not
copy a model or free the incumbent before constructing its replacement.
The candidate already had to be constructed and coexist with the incumbent
through fresh evidence. Preparatory metadata, old/new evidence records and
the receipt must additionally fit their actual allocated peak.

This primitive is meaningful even for tight role capacities. With two
one-byte objects, one currently owned by deployment and one by Compiler,
and a one-byte cap for each role, acquiring the candidate for deployment
before releasing the old lease falsely exceeds the deployment cap. A
registered simultaneous lease exchange has one byte per role both before
and after, while retaining both actual buffers throughout. It is legal
only because this CPU machine explicitly implements that atomic transfer.
It is not a claim that an arbitrary copy-based GPU install has the same cost.

## 3. Exact lease-map preparation

For each object o and owner a let n[a,o] be the original positive reference
count. A batch contains moves `(a,b,o,c)` and explicit releases `(a,o,c)`.
First add **all debits against the original map**. Every total debit must
be at most n[a,o]; a credit from another move cannot manufacture an original
lease for a later debit in the same batch. Apply all debits and credits to
a detached proposed map, then retire exactly objects with no remaining
owners. An owner can close only if no proposed reference remains for it.

Compute total residency once per actual object and role residency once per
role represented among that object's owners. Validate the complete resulting
map against the registered caps. No fictitious intermediate acquire/free
ordering substitutes for the registered simultaneous primitive. Preserve
all old cumulative work and peaks and update peaks with the final map.

[`ResourceLedger.prepare_transfer`](../../src/reference_compiler/fp_reference/resources.py)
does this without modifying its source ledger. It copies every registered
mutable ledger coordinate and rejects unknown fields rather than assuming
that they are irrelevant. The returned ledger is only a proposed accounting
state; no public Runtime API accepts a caller-supplied ledger as authority.
Runtime constructs it from its actual allocations and publishes it together
with the corresponding actual buffer dictionary and complete semantic root.

## 4. Preparation and one publication point

Installation requires an idle ordinary boundary, current matching lineage
states and two completed optimizer accumulators. A crossing at a partial
optimizer unit cannot erase that accumulator or move the structural cursor.
The fixed serialized Runtime has no in-flight asynchronous worker, device
kernel or hidden scheduler continuation. Paused search cursors are explicit
immutable data with registered future continuation methods.

Before publication, Runtime:

1. records a unique attempt and charges its registered work;
2. checks historical selected-lineage provenance and both current persistence
   identities, plus the current complete exact/binary64 state relation;
3. creates fresh destination/workspace owners and physically allocates every
   replacement metadata record and prepared receipt against the old ledger;
4. prepares the exact ownership map, persistence invalidations and search
   closures while retaining the old deployed root and learner objects;
5. verifies that each retained learner record differs only in its declared
   physical-owner coordinate and that every learner buffer is the identical
   existing Python buffer object;
6. constructs the entire next root, its routers, actual buffers and result.

Only then does `self.__dict__ = next_root` publish the prepared root. This
single root replacement is the linearization point for the registered
serialized CPython machine. Every fallible allocation, validation, ledger
preparation and result construction precedes it. There is no later numerical
transform hidden under the first install's evidence.

The frame is explicit:

| Complete coordinate | Registered effect |
|---|---|
| Ordinary cursor, observations, targets, source contexts, data-use ledger | Preserved; installation consumes no new exogenous event |
| All exact/binary64 parameters, gradients, delayed queues and learner clocks | Preserved exactly; current learner buffers keep identity |
| Deployed lineage and ownership | Target becomes deployed; old deployed lineage becomes a retained shadow under fresh owners |
| Other candidates and retained code/profiles/event/bridge history | Preserved, including unresolved retained candidates and all required leases |
| Search/frontier records | Closed with their original cursor/rows/witness history retained; no later job side effects or continuation |
| Proof issuance history | Retained as history; current class-proof access rejects the closed/stale context |
| Persistence identities | Live/crossed identities become unresolved for the changed deployed base; histories and crossing wealth remain data |
| Alpha/error allocation | Preserved with no refunds or transported statistical authority |
| Objects, leases, closed/retired IDs, current/peak/cumulative resources | Prepared and published consistently with actual buffers and work |
| Claim, program/source/learner rules, identity counters and other registered metadata | Carried in the complete root, with the attempted install/revision increments recorded |

The implementation checks the complete registered root-field schema. A
future job/RNG/cache coordinate does not automatically inherit this version's
quiescence/frame proof. It must receive an explicit transition interpretation.
An unknown field prevents this install instead of being silently omitted.

**Scoped transition theorem.** Under this fixed schema and serialized machine,
a completed `install_cpu` has exactly the target complete learner states at
the original exogenous cursor, the declared shadow/search/statistical policy,
and a valid actual object/lease/resource map at the same publication point.
The numerical post-install relation follows by identity transport of the
already checked states; no approximate-equivalence composition is used.
This is a registered structural transition, not a task-free equivalence or
simulation of the whole old/new self-Compiler.

## 5. Failure is not restoration of the entire past

A failure before publication cannot publish a half-installed learner or
partly transferred model lease map. It releases only the newly prepared
objects and closes the new unused owners. Old learner, persistence and
search records remain. Current paired evidence may still be used by a later
paid attempt if those old trajectories remain continuous.

The complete failed state is **not** the original Omega: attempted identities,
Compiler revision, actual work, peak residency, retired physical IDs and
failure diagnostics remain changed. Search proofs may therefore be stale
even when numeric learners are unchanged. This is not a resource refund or
an equivalence assertion. If cleanup itself fails, the prefix halts rather
than permitting use of an unaccounted workspace.

Audit exposed a concrete retry bug. Initially a prepared invalidation used
only the old record's next generation as its object ID. Aborting retired that
physical identity, but a retry generated the same ID while the unchanged old
logical record still had the same generation. The ledger correctly rejected
recycling it. Prepared metadata now includes the unique install-attempt ID.
The old logical state can remain intact while every physical attempt has
its own nonreusable identity. No counter is reset to hide the failed work.

Receipt bytes can be prepared before publication, but the authoritative
install-receipt history receives an `INSTALLED_CPU` record only in the
published root. A failed prepared receipt is not an installed-state token.
The generic target `install` port still returns UNRESOLVED; it cannot accept
CPU records as actual AMP authority.

## 6. Executed audit and remaining gates

Run `python -B scripts/audit_cpu_installation.py --write`. The independent
lease oracle checks 2,016 cases, including 649 feasible atomic transfers.
Its exact finite test class has two objects of sizes one and two, two owners,
each reference count in {0,1,2}, each role cap in {1,2,3}, all initially legal
maps, and twelve declared one-/two-move patterns (including repeated debits
and attempted credit laundering). Separate adversaries check release/closure
and unknown state. This is not exhaustive enumeration of arbitrary batches.
The full Runtime first exhausts 35- and 774-member native constructor classes,
then executes fresh four-path evidence and installs their selected continued
learners. The larger case installs a nonzero parameter state changed by
ordinary learning. Independent binary64 replay covers the continuation
before and after installation. Observational line tracing sees exactly the
old root and then the complete new root, with no partially published metadata.

Endpoint adversaries include wrong-path/fake proof IDs, a same-graph newborn,
partial optimizer units, a paused search, stale reference proof access,
unknown Runtime job state, late preparation failure and legal paid retry.
Actual immutable byte/work caps reject a target whose existing model buffers
fit but whose install preparation does not. No failed attempt borrows future
resources, transfers evidence or refunds alpha.

A continued test performs two complete 35-member searches and installations
in the same Runtime, at cursors 22 and 38. The second proposal compares
against the actually installed baseline and starts new evidence at cursor
24 with new identities and unit wealth. Both search classes and the later
alpha rules were registered before execution. Both generations keep their
receipts and end old statistical authority. The four allocations consume
the global alpha of 3/4; a third admission is refused despite a live shadow
and sufficient unread horizon. Independent binary64 replay checks 306 phases
through ordinary continuation after the second install. This tests one
nontrivial later Compiler continuation, not every possible future policy.
